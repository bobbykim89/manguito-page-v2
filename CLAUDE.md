# Manguito Page v2

Photo blog for Manguito, a peach-faced lovebird. Nuxt 4 (Vue 3) frontend and a Nitro/H3 API in one repo, with MongoDB via Mongoose. Images are hosted on Cloudinary, password-reset emails go out through Nodemailer (Gmail), and client state lives in Pinia. Features: a photo grid and post pages with comments, JWT auth with signup, login and email password reset, and an admin area (posts, comments, users, access requests). Installable PWA. Deployed on Vercel (https://manguito-page.bobbykim.dev/).

Current focus: the improvement backlog in GitHub issues #11–#22 (tooling, component-library upgrade, dependency bumps, backend refactor, stores refactor, infinite scroll, image uploads, hydration, accessibility, About page, dashboard). Prefer small, verifiable changes over sweeping rewrites. When an issue changes a convention below (e.g. #16 stores), update this file in the same PR.

## Toolchain

- Node **24** (`.nvmrc`; run `nvm use` first). `engines.node` is `24.x` (pinned so Vercel can't move to a later major on its own; `test/unit/nodeVersion.test.ts` keeps it matching `.nvmrc`).
- pnpm **12** pinned via `packageManager` (use corepack). Build scripts must be explicitly allowed in `pnpm-workspace.yaml` under `allowBuilds`; pnpm 12 fails the install on unapproved ones.
- Vercel uses the pinned pnpm because the project sets `ENABLE_EXPERIMENTAL_COREPACK=1`.
- The build scripts run `nuxt prepare` before `nuxt build`. The build's type check (`typeCheck: 'build'`) reads the root `.nuxt/` (auto-import types), which only `nuxt prepare` writes, and Vercel restores a cached `.nuxt/` and skips the postinstall when the install is "Already up to date", so without it a PR that adds a composable fails with `Cannot find name 'useX'`.
- Held back on purpose: TypeScript stays on 6.0 (7.0 is the native compiler, which `vue-tsc` doesn't support yet) and `@types/node` on 24 (the runtime is Node 24). Tailwind 4 runs through its Vite plugin (`@tailwindcss/vite` in `nuxt.config.ts`), not PostCSS.

**Tests:** Vitest runs two projects (`vitest.config.ts`):

- `api`: `test/api/` and `test/pages/`. The global setup (`test/setup/global.ts`) builds the app with the fake values in `test/test.env` (never the real `.env`), starts it against `mongodb-memory-server` (via `NUXT_MONGO_URI`, see `server/utils/mongoUrl.util.ts`) with require-of-ESM disabled (like Vercel), and the tests call the real `/api` routes (`test/utils/api.ts`) and render real pages. `test/utils/db.ts` connects to the same memory DB for setup and assertions. Set `SKIP_BUILD=1` to reuse an existing `.output` when only tests changed. Mail and Cloudinary never leave the machine: `test/setup/fakes.ts` runs a local SMTP sink (`NUXT_MAILER_*`) and a fake Cloudinary API (`CLOUDINARY_URL` with `upload_prefix`), and tests read what they received with `sentMail()` / `cloudinaryCalls()` from `test/utils/fakes.ts` (call `resetFakes()` first); `failNext('mail' | 'cloudinary')` makes the next call fail. Assert errors with `expectApiError(res, code, message?)` (`test/utils/api.ts`); `signup()` (`test/utils/auth.ts`) makes a real user with a known password. `test/pages/a11y.test.ts` runs axe-core (WCAG 2.0 A/AA) over the server-rendered HTML of every page and session in jsdom; add a row to its `matrix` for a new page.
- `unit`: `test/unit/`, client stores, composables and pure server helpers in the Nuxt environment (happy-dom), loading `test/test.env`. Call `resetState()` from `test/unit/helpers.ts` in `beforeEach`; mock API routes with `mockApi(method, url, handler)`, answering `okEnvelope(data)` or `failEnvelope(event, code, message)`, and remove them with `clearApiMocks()` in `afterEach`. Set a session by patching `userStore.currentUser` (the other auth fields are derived). Stores mounted pages read live in `useNuxtApp().$pinia`, not the one `resetState()` activates. After adding a composable, clear `node_modules/.cache/nuxt` and `node_modules/.vitest-cache`, or the unit project won't auto-import it.

CI (`.github/workflows/ci.yml`) runs two jobs on every PR: `lint` (`pnpm lint`, `pnpm format:check`) and `test` (`pnpm typecheck`, `pnpm test`). Both are required checks on `master`. Run `pnpm lint` and `pnpm format` before committing; also exercise UI changes in `pnpm dev`.

## Conventions

- **API routes are thin.** Each `server/api/**/<name>.<method>.ts` only wires middleware and a controller method:
  ```ts
  export default defineApiRoute({
    middleware: [checkAuth],
    handler: postController.updatePost,
  })
  ```
  `defineApiRoute` (`server/utils/defineApiRoute.util.ts`) runs each middleware (plain `(e) => void` functions that throw to refuse), then the handler, and answers `{ ok: true, data }` (status 200, or `status: 201` on creates) or the error envelope. Unknown `/api` paths and methods hit `server/api/[...].ts` (404 `NOT_FOUND`). Logic lives in class-based controllers (`server/controller/<domain>/<domain>.controller.ts`), exported as singletons from `server/controller/index.ts`. A new post's middleware runs `requireRole(...)` (`server/utils/requireRole.util.ts`), then `readFormDataText`, then `uploadCloudinary`, so a refused or incomplete request never reaches Cloudinary. `uploadCloudinary` judges the file by its bytes (`detectImageType`: JPEG, PNG or WebP, never the declared type) and refuses an empty one (400) or one over `UPLOAD_BUDGET` (4 MB, `shared/dto/limits.ts`; 413 `PAYLOAD_TOO_LARGE`); `createNewPost` deletes the uploaded image if the post then fails to save. Check route param and body ids with `parseObjectId(...)` before querying.
- **Validation:** request bodies go through Zod schemas in `shared/dto/<domain>/` via `readValidatedBody(e, schema.parse)`. A failure answers 400 `VALIDATION_FAILED` with one `details` entry (`{ path, message }`) per invalid field. Length limits and their messages live in `shared/dto/limits.ts` (`LIMITS`, `LIMIT_MESSAGES`, and the trimmed `emailSchema`, `captionSchema`, `commentTextSchema`, `usernameSchema`); the schemas mirror them as `maxlength`, and the client forms import the same constants. Emails are trimmed and lowercased, so lookups ignore case; usernames are unique as typed.
- **Database:** indexes are declared on the Mongoose schemas and built by `autoIndex` once a request has loaded the models (unique `email`, `name` and `tokens.userId`; `posts.date`; `comments.post`). Before adding a unique index, run `scripts/check-db.ts` against the remote databases. Use `.lean()` only where no returned field (populated ones included) has a schema default: production has old users without `role`/`updatedAt` and posts without `updatedAt`, which only hydrated documents fill in.
- **Errors:** every `/api` response is `{ ok: true, data }` or `{ ok: false, error: { code, message, details? } }` (types and `API_ERROR_STATUS` in `shared/types/api.types.ts`). Throw `apiError(code, message)` (`server/utils/apiError.util.ts`); `message` is shown to users, so write a sentence and never include internals. Codes: `VALIDATION_FAILED` 400 (bad body, bad id, missing field), `UNAUTHENTICATED` 401 (no, bad or dead session), `INVALID_CREDENTIALS` 401 (wrong login or current password), `FORBIDDEN` 403 (role or ownership refusal), `NOT_FOUND` 404, `CONFLICT` 409 (taken email or name), `PAYLOAD_TOO_LARGE` 413 (an upload over `UPLOAD_BUDGET`), `UNSUPPORTED_MEDIA_TYPE` 415, `UPSTREAM_FAILED` 502 (Cloudinary, mail), `INTERNAL` 500. Anything else thrown is logged and answered `INTERNAL` with a generic message (`toApiFailure`). On the client, call the API with `useNuxtApp().$api` (adds the token, unwraps `data`, throws `ApiError` with `status`, `code`, `details`) or `useApi` (`useFetch` through the same instance; its error is a `NuxtError` whose `.data` is the envelope, since the class doesn't survive the SSR payload). `useErrorCheck().extractMessage` reads either (a `VALIDATION_FAILED` with exactly one `details` entry gives that entry's message); `isAuthError` is true only for code `UNAUTHENTICATED`, never by status. Run every API action through `useApiAction().run(() => $api(...), { success?, quiet? })`: it shows the success alert, or on failure ends a dead session (`userStore.expireSession()`) and alerts the message, and resolves `{ ok: true, data }` or `{ ok: false }` without throwing. A caller's own `onRequest`/`onResponse` on `$api` run after the plugin's token and unwrapping. `app/error.vue` shows the real status: 404 says the page doesn't exist, other 4xx show `statusMessage`, 5xx show a generic message (never server internals).
- **Auth:** `POST /api/auth` (and signup) return `data: { accessToken: "Bearer <jwt>" }`. The client stores it in the `access_token` cookie (`useAuthToken`, 7 days) and sends it verbatim as the `Authorization` header. `server/utils/checkAuth.util.ts` (async) verifies it, sets `event.context.user`, and loads the user through the per-request DataLoader (`server/utils/userLoader.util.ts`). Controllers and `requireRole` get the user with `getCurrentUser(e)` (hydrated, no password), never their own `findById`, so a request reads its user once; after changing the user, use what the write returned. A valid token whose user no longer exists gets **401** `UNAUTHENTICATED`, `Session expired, please log in again` (not 404). Tokens are signed by `signSessionToken(user)` with `{ id, v: tokenVersion }`; an email password reset bumps `tokenVersion`, which logs out every device (same 401), while a settings password change doesn't. A missing `v` or `tokenVersion` counts as 0. The user schema's `toJSON` drops `password` and `tokenVersion`. `useAuthToken` returns one shared cookie ref per app instance. Roles are `ADMIN`, `MANAGER`, `USER`; role checks live in each controller method.
- **Client state:** Pinia setup stores in `app/stores/` hold only state several pages share: `userStore` (the session: `currentUser`, `sessionExpired`; getters `isAuthenticated`, `role`, `isAdmin`, `isManagerOrUp` derived from `currentUser`), `postStore` (the post list the grid and `/admin/posts` share, loaded a page at a time: `posts`, `nextCursor`, `status` (`idle`/`loading`/`error`/`done`), `loaded`; `loadFirstPage()`, awaited in those pages' setup so page one renders on the server and hydrates without a refetch (it does nothing while hydrating, so a page one that failed on the server shows its error and Try again); `loadMore()`, one at a time, skipping ids it already has; `retry()`; create/update/delete; and `gridScrollTop`) and `alertStore`. Store actions are "run the call, update state"; they don't repeat the server's permission rules. `app/plugins/init.plugin.ts` (`dependsOn: ['api']`) runs only `userStore.ensureAuth()` on `app:created` (posts load where they're shown: the grid and `/admin/posts` through `postStore`, the home page asks for `limit: 7` itself, the post page through `usePost`); `ensureAuth` is the current-user check, at most once per app instance. An `UNAUTHENTICATED` error from any action logs out through `userStore.expireSession()`: **quietly** for the startup check, with the message for actions the user started. `sessionExpired` is set only when a held session is rejected, and logout, login and signup clear it. `FORBIDDEN`, `INVALID_CREDENTIALS` and other errors only alert. The route guards (`adminRoute`, `authRoute`, `guestRoute`) `await userStore.ensureAuth()` first, so they also run during the server render; on a protected page an expired session goes to `/auth/login?reason=expired` (the login page explains it), no session goes to `/` (the guard's alert shows only on client-side navigation; on a first-load 302 it's lost).
- **Client layout:** `app/stores/<thing>Store.ts` exports `use<Thing>Store`, for shared state only. `app/composables/use<Thing>.ts` holds functions that need the Nuxt context: the API client (`useApi`, built with `createUseFetch` so each call site gets its own key; `useApiAction`; `useErrorCheck`; `useAuthToken`), page data (`usePost` for the open post and its prev/next links from the server, throwing a fatal 404 for an unknown or malformed id; `usePostComments`; `useAccountSettings` for the layouts' account forms) and `useImageUrl.ts`, the one class among them (`ImageUrl`, which reads the runtime config). A page keeps its own data inline when it's one list and an action or two (the admin pages); it moves to a composable when it carries logic worth testing or two places share it. `app/utils/` holds pure functions and classes with no Nuxt context (`apiError.ts`, `passwordRule.ts`, `gridScroll.ts`, `fitImage.ts`, `prepareUpload.ts`, `uploadWithProgress.ts`, `postAlt.ts`). Never resolve a store after an `await`: in SSR it could belong to another request.
- **Post paging:** `GET /api/post?limit&cursor` answers `{ posts, nextCursor }`, newest first (`date`, then `_id`, descending); `limit` is 1–50 (default 30), and `cursor` is the previous page's opaque `nextCursor` (`<epoch ms>_<id>`, filtered with `olderThan` in `server/utils/postCursor.util.ts`), so posts created or deleted between pages neither repeat nor shift. `GET /api/post/:id` answers `{ post, prevId, nextId }`, wrapping at both ends. `<LoadMoreStatus>` (`app/components/posts/`) follows a list of the shared posts: its sentinel (`useIntersectionObserver`, about a screen early) loads the next page, it shows the loading/end/empty/error-with-Try-again line, and announces changes in a polite live region; after an error it waits for Try again. Coming back to `/posts` from a post page returns to where the grid was: `app/plugins/gridScroll.client.ts` saves `window.scrollY` in `postStore.gridScrollTop` on grid → post, and `app/router.options.ts` (Nuxt's default scroll behaviour plus `scrollTarget` from `app/utils/gridScroll.ts`) restores it; a saved back/forward position still wins, and other ways into `/posts` start at the top.
- **Image uploads:** the new-post modal never sends the picked file as-is. `prepareUpload` (`app/utils/prepareUpload.ts`, browser only) decodes it with `createImageBitmap` (applying the phone's rotation), and `fitImage` (`app/utils/fitImage.ts`, pure) re-encodes it as JPEG at most 2400 px on the long side, at the highest quality from 0.92 down to 0.6 that fits `UPLOAD_BUDGET`, shrinking the dimensions by 0.85 only when even 0.6 doesn't fit. Re-encoding drops EXIF (location) and keeps every upload under Vercel's 4.5 MB request limit. HEIC is refused with a message (iOS Safari converts it itself because the input accepts only `image/jpeg,image/png,image/webp`); inputs over 50 MB are refused before decoding. `postStore.createNewPost(form, { onProgress })` uploads through `uploadWithProgress` (XMLHttpRequest, for progress; it throws `ApiError` like `$api`, and turns Vercel's bare 413 into `PAYLOAD_TOO_LARGE`) and returns whether the post was created; the modal keeps its form until then, also when it's closed mid-upload. Tests never reach the real Cloudinary: the API tests use the fake, and browser checks intercept `POST /api/post`.
- **Component library** (`@bobbykim/manguito-theme` 1.x, `mcl-*`): open `Modal`/`Sidebar` through their template ref (`open()`/`close()`), and build collapsibles from `Collapse` in an `<AccordionGroup>` with `useCollapseTrigger` (from `@bobbykim/manguito-theme/composable`) on the trigger button. `v-toggle`/`v-collapse` don't work. Use the 1.x prop names (`custom-class`, `show-*`, `MclFormGroup`'s `field-id`); Vue passes unknown props through silently, so `test/unit/libraryMigration.test.ts` bans the old ones. Show form errors by binding `:invalid` (with `invalid-feedback`); native validity no longer shows them. The theme's background utility is `mcl-bg-*`, so fade a color with Tailwind's `bg-<color>/<opacity>`, not `bg-opacity-*`. The theme's spacing tokens (`--spacing-xs` … `--spacing-3xl`) also win over Tailwind's container sizes, so `max-w-md` is 2rem, not 28rem: write the width out (`max-w-[28rem]`). `isomorphic-dompurify`'s jsdom is pinned to 25 in `pnpm-workspace.yaml` because newer jsdom breaks SSR on Vercel; keep the pin.
- **Hydration:** the server render and the browser's first render must match. Browser-only APIs (window, `confirm`, image work) run in handlers or behind `import.meta.client`, and nothing that differs between server and browser decides what renders: not feature detection (hence `useClipboard({ legacy: true })` on the post page, so `isSupported` is true on both), not `new Date()` text, not the timezone. Show dates with `<LocalDate :datetime>` (`app/components/LocalDate.vue`: `<NuxtTime>` in en-US, rewritten to the visitor's timezone before hydration), or `<NuxtTime>` directly for other formats. `<ClientOnly>` and `data-allow-mismatch` are banned by `test/unit/hydrationSuppressions.test.ts`: fix the cause instead.
- **Accessibility (WCAG 2.0 AA):**
  - The layouts give every page a "Skip to content" link and `<main id="main">`; each page has exactly one `<h1>` (visually hidden with `sr-only` where the design has no title, as on the post page), with no skipped heading levels.
  - Colours only through the theme tokens (`--mcl-*` overrides live in `app/assets/css/styles.css`); every new text/background pair gets a row in `test/unit/contrast.test.ts` (4.5:1, or 3:1 for large text). `text-dark-1` and light-3 text on pink buttons fail and are banned.
  - Every field has a visible label (`MclFormGroup`'s `label`); a control's name matches its visible text or what it acts on; anything clickable is a `<button>` or a link, never a clickable `div` (hence Home's `FlipCard`, not `MclCardC`). Photos are named with `postAlt(caption)`.
  - Decorative animation stops within 5 s (`animate-bounce-settle`, not `animate-bounce`; checked by `test/unit/motion.test.ts`), and nothing decorative moves under `prefers-reduced-motion` (the loading spinner excepted). Live regions announce stages, not every change.
  - `test/pages/a11y.test.ts` is the gate; jsdom has no CSS, so contrast and keyboard behaviour also get a browser walk before merge.
- **Style:** Prettier (single quotes, no semicolons, 2-space indent, Tailwind classes sorted by `prettier-plugin-tailwindcss`), checked in CI. TypeScript strict. A deliberately unused binding starts with `_`. Match the surrounding code.

## Guardrails

- Do **not** read, print, or edit `.env` / `.env.*`. If you need to know which variables exist, look at `runtimeConfig` in `nuxt.config.ts`; `test/test.env` lists them with fake values.
- `pnpm dev:dev`, `dev:prod`, `build`, `build:dev` and `build:prod` point at remote services with real data. Don't run anything that writes data against them without asking. Use `pnpm dev` / `build:local` with the local DB.
- `master` is protected: work on a branch and open a PR; `lint` and `test` must pass. PRs are merged with merge commits (keeps `.git-blame-ignore-revs` hashes valid). Commit messages follow Conventional Commits with a path scope, e.g. `fix(server/controller/): ...`, `feat(app/stores/): ...`.
